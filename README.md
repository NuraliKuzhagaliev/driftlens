# DriftLens

**Configuration release gate for small teams.** A required environment variable can work on a developer's machine but disappear from the example file or deployment manifest. DriftLens traces the same contract across application source, `.env.example`, and `compose.yaml`, blocks the release when required keys are missing, suggests specific repairs, and verifies them on a second run.

## Start in under a minute

Requirements: Python 3 for serving files; Node.js 18+ for tests. No installation or API key is required.

```bash
python3 -m http.server 8080
```

Owner preview: https://driftlens-release-gate.nurali6002217.chatgpt.site (currently private; grant judge access before submitting).

Open http://localhost:8080 and click **Run release gate**. From the `driftlens` directory, run `npm test` to verify the detector. Alternatively host this static folder on GitHub Pages or any static host. Opening `index.html` as a `file://` URL cannot load fixture files in most browsers.

## Incident to Guard

The **Incident to Guard** flow lets you trace a live crash back to the release contract. Paste or load a service log; DriftLens extracts the missing variable, correlates it with open release-gate findings, and displays a four-step causal chain: incident → source reference → missing setup/deployment entries → proposed repair.

### How to use it

1. Run a release-gate scan first (click **Load broken sample** then **Run release gate**).
2. Scroll to the **Incident to Guard** section and click **Load sample log**.
3. Click **Analyse log** to see the causal chain for `PAYMENT_API_KEY`.
4. Paste your own log or click **↑ Load file** to analyse a real incident.

### Recognised log patterns

| ID | Runtime | Pattern example |
|----|---------|-----------------|
| `py-keyerror` | Python | `KeyError: 'PAYMENT_API_KEY'` |
| `py-none-env` | Python | `TypeError: … NoneType … os.getenv("KEY")` |
| `node-missing-env` | Node.js | `process.env.KEY is not defined` |
| `node-must-set` | Node.js | `Error: Must set KEY environment variable` |
| `node-required-env` | Node.js | `Missing required environment variable: KEY` |

The analyser returns **"unrecognized log"** for any log that does not match one of the patterns above. It never invents a root cause.

## Scope and limits

- Input is pasted or uploaded locally; source is never sent from the browser.
- Supports Python `os.getenv` / `os.environ` and JavaScript `process.env` static references, ordinary `.env` assignments, and simple Compose `environment` mapping/list values.
- Does not resolve runtime secrets, YAML anchors, generated keys, or correctness of secret values. A READY verdict means the checked static contract is consistent, not a guarantee of deploy success.
- The sample fixtures are original, synthetic, and contain no actual credentials or personal data.

### Incident-to-Guard limitations

- Only the five patterns listed above are recognised; all other log formats return "unrecognized log".
- The Python `py-none-env` pattern requires both `TypeError` and the `os.getenv(…)` call to appear within two lines; deeply nested tracebacks may not match.
- Variable names must be uppercase and match `[A-Z][A-Z0-9_]*`; lowercase or mixed-case names are ignored.
- Correlation requires a release-gate scan to have been run in the same browser session; without a scan, the chain can identify the variable but cannot link it to contract findings.
- The incident analyser only reads logs that are pasted or loaded locally; no log shipping or live-tail integration is provided.
- A causal match ("CAUSAL MATCH") proves only that the variable has an open static finding — it does not prove the static finding caused the runtime crash.

## Command-line release gate

`bin/check-release.js` runs the same analysis engine from the terminal, making it easy to block a CI pipeline when required environment variables are absent.

### Quick start

```bash
# Default run — uses the sample broken fixtures (expects HOLD exit code 2)
node bin/check-release.js

# Point at your own files
node bin/check-release.js \
  --source     src/app.py \
  --example    .env.example \
  --deployment docker-compose.yaml \
  --contract   config/contract.json

# Machine-readable JSON report
node bin/check-release.js --json | jq .status
```

### Exit codes

| Code | Meaning |
|------|---------|
| `0`  | **READY** or **REVIEW** — no blockers; deployment is allowed |
| `1`  | Invalid input — unreadable file, bad contract, or unknown flag |
| `2`  | **HOLD** — one or more blockers found; deployment is blocked |

### Using as a CI gate

Add a step to your pipeline (GitHub Actions example):

```yaml
- name: DriftLens release gate
  run: node bin/check-release.js
  # exits 2 → step fails → pipeline stops before deploy
```

Or capture the JSON report as an artefact:

```yaml
- name: DriftLens release gate
  run: node bin/check-release.js --json > driftlens-report.json
- uses: actions/upload-artifact@v4
  with:
    name: driftlens-report
    path: driftlens-report.json
```
